# 로마스토어 E2E 재검토와 재설계안

검토일: 2026-09-07, 기준 커밋: `1f6c89b`. 실행 코드와 TC 원본은 변경하지 않았어.

**추천: Playwright와 기존 TC ID는 유지하고, CSV는 검증 명세를 관리하는 용도로 정리하자. 실제 구매 흐름은 TypeScript spec과 테스트별 fixture에서 직접 검증하는 구조가 적합해.**

현재 가장 큰 문제는 케이스 수가 아니라 성공 판정의 약함이야. 화면이 보여도 수량, 상품, 금액, 선택 상태가 잘못될 수 있는데 이를 구분하지 못해. 전면 교체보다 기존 실행 결함을 먼저 복구하고, 핵심 흐름부터 점진적으로 이관하는 게 좋아.

## 2. 우선 수정할 발견 사항

여기서 P1, P2는 **자동화 개선 우선순위**야. 서비스 결함 심각도와는 구분해.

### F01. P1: 결과 요약 스크립트가 문법 오류로 실행되지 않아

- 근거: `scripts/summarize-results.mjs:33-43`, 특히 39행.
- HTML을 감싸는 템플릿 문자열 내부의 `test-health.md`에 백틱을 다시 사용해 문자열이 끊겨.
- `node --check scripts/summarize-results.mjs`와 실제 스크립트 실행 모두 `SyntaxError: Unexpected identifier 'test'`를 반환했어.
- `.github/workflows/scheduled-tests.yml`의 요약 단계가 결과를 만들지 못해. 요약 output과 이메일 첨부 생성도 영향을 받아.
- 수정: HTML의 `<code>test-health.md</code>`로 바꾸고, CI에 `.mjs` 문법 검사를 추가하자. 이번 TypeScript 검사만으로는 이 오류가 검출되지 않았어.

### F02. P1: 상품과 주문 결과가 틀려도 테스트가 통과할 수 있어

- 근거: `testcase-management/steps.csv:17-23`, `59-67`, `automation/runner/interpreter.ts:60-67`.
- CART-002는 수량 증가, 감소 후 주문 버튼만 확인해. 수량이 그대로여도 통과할 수 있어.
- CHECKOUT-003은 결제수단 클릭 후 같은 radio의 노출만 확인해. 실제 선택 상태, 다른 수단의 해제 상태를 검증하지 않아.
- SEARCH-002, STORE-002는 정렬 후 제목이나 정렬 링크만 확인해. 상품 가격 순서는 검증하지 않아.
- HOME-002는 클릭한 탭의 노출만 확인해. 선택 상태와 대응 패널을 확인하지 않아.
- PRODUCT-003, CART-001은 추가한 상품의 식별값, 수량, 금액을 확인하지 않아.
- 수정: 수량 전후 값, 선택 상태, 상품 행의 일치, 금액 계산, 정렬 결과를 기대 결과로 정하자. 보이는지 확인하는 assertion 자체는 필요하지만 결과 검증을 대신할 수 없어.

### F03. P1: 전역 셀렉터 병합이 다른 화면의 정의를 덮어써

- 근거: `automation/runner/selectors.ts:10-16`, `selectors/search.yaml:29-34`, `selectors/store.yaml`.
- `Object.assign`으로 같은 이름의 element를 아무 검증 없이 덮어써.
- 실제 `loadSelectors()` 호출 결과, `sort_price_asc`는 스토어의 `role: link`, `name: 가격낮은순`으로 결정됐어. 검색 파일의 `낮은가격순` 정의는 사라져.
- 중복 element 이름은 8종이며, 그중 가격 오름차순과 내림차순은 파일 간 값도 달라. 수량, 찜하기도 전역 이름을 공유해.
- 수정: 이관 전에는 `search_sort_price_asc`, `store_sort_price_asc`처럼 이름을 분리하고 중복 키를 즉시 오류로 처리하자. 이관 후에는 SearchPage, StorePage 등 각 화면 안에서 locator를 소유하자.

### F04. P1: 현재 검색 UI와 locator의 역할이 달라

- 근거: `selectors/search.yaml:8-10`, `17-34`, 2026-09-07 현재 DOM.
- 검색창은 `searchbox "상품 검색"`인데 코드는 `textbox`로 찾고 있어. 저장된 과거 실패 화면에서도 같은 차이를 확인했어.
- 검색 결과 정렬은 현재 `button "인기순"`, `button "낮은가격순"`이야. 검색 YAML에는 `link`로 정의되어 있어.
- 반면 스토어 정렬은 현재도 `link "가격낮은순"`이야. 검색과 스토어를 같은 locator로 처리할 수 없어.
- 수정: 검색 영역을 먼저 특정하고 현재 역할로 변경하자. 입력 역할 수정만으로 검색 전체가 복구됐다고 판단하면 안 돼. 입력, 제출, 검색어 반영, 결과 목록까지 다시 실행해야 해.

### F05. P1: 주문자와 수령자 입력을 구별할 수 없어

- 근거: `selectors/checkout.yaml:9-23`.
- 주문자 성함과 수령자 성함이 모두 전역 `getByRole('textbox', { name: '성함' })`으로 해석돼. 휴대폰번호도 동일해.
- 두 입력이 함께 존재하면 strict mode 오류가 나고, 한 입력만 보이면 잘못된 대상에 입력할 수 있어.
- 확인된 사실은 **정의가 같고 범위 구분이 없다는 것**이야. 주문서 현재 DOM은 이번에 확인하지 못했어.
- 수정: 주문자와 배송지 영역, 연결된 label 또는 고유 test id로 범위를 분리하자. 재설계 검증에는 두 사람의 서로 다른 이름과 번호를 써서 잘못된 입력을 잡아내자.

### F06. P2: quarantine 설정은 실행에 반영되지 않고, skip 사유도 재평가가 필요해

- 근거: `automation/tests/run-testcases.spec.ts:20-24`, `30-45`, `automation/runner/known-issues.ts`.
- `manual`, `enabled=false`만 제외하고 `quarantine`은 실행해. CSV에 quarantine을 적어도 실행 분리가 되지 않아.
- CSV는 PRODUCT-001, PRODUCT-002까지 모두 active지만 코드가 별도로 skip시켜. 상태 정보가 두 곳에서 달라.
- 현재 대표 상품의 상품명 heading은 main 범위에서 정확한 이름으로 1개, `총 1개`도 정확한 텍스트로 1개였어. `product-title` test id는 0개였어.
- test id가 없다는 사실만으로 자동화 불가능을 뜻하지 않아. 현재 DOM에서는 상품명 검증을 재개할 대안이 확인돼. 수량 변경 후 상태의 안정성은 추가 실행이 필요해.
- 수정: 상태, 사유, 담당자, 이슈, 재검토일을 명세 한 곳에서 관리하자. quarantine은 별도 실행 범위로 분리하고 정상 통과율에 섞지 말자.

### F07. P2: 장바구니 준비 단계는 있지만 성공을 보장하지 않아

- 근거: `testcase-management/steps.csv:31-39`, `automation/runner/interpreter.ts:39-46`, 기존 PRODUCT-003 실패 화면.
- 상품 상세 이동, 담기 클릭, `/cart` 이동을 하는 케이스가 11개야. CART-001과 checkout에도 준비 단계가 이미 있어.
- 담기 클릭 직후 성공 상태를 확인하지 않고 문서 이동을 해. 추가 완료 전 이동, 클라이언트 초기화 시점, 서버 응답 실패 등을 구별하지 못해.
- 과거 실패 화면에서 장바구니가 비어 있었다는 사실은 확인돼. **원인이 요청 중단이나 초기화 경쟁이라는 건 가설**이야. 새 trace와 응답, UI 완료 상태 대조가 필요해.
- 수정: 테스트별 `cartWithProduct` fixture에서 대상 상품, 구매 가능 상태를 확인하고 담기 완료 후 해당 상품 행과 수량을 확인하자. UI 담기 자체를 검증하는 spec은 이 과정을 테스트 본문에 남기자.
- `test-health.md`의 준비 단계 누락 진단은 현재 코드와 맞지 않아. 준비 존재 여부와 준비 성공 여부를 나눠 기록해야 해.

### F08. P2: 입력 검증과 실행 결과 분류에도 빈틈이 있어

- `automation/runner/loader.ts:46-53`: 존재하지 않는 fixture 경로는 오류 대신 빈 문자열이 돼. `${checkout.missing}`을 실제 함수에 전달해 빈 문자열 반환을 확인했어.
- `scripts/sync-testcases.mjs`: TC ID 중복 검사는 있지만 생성 경로 중복 검사, fixture 변수 존재 검사, custom 함수 등록 여부 검사는 없어. 이 부분은 코드 검토로 확인했고 잘못된 CSV를 저장소에 주입하진 않았어.
- `scripts/summarize-results.mjs:8,18-20`: flaky를 실패 수에 더하면서 마지막 시도가 실패인 항목만 목록에 담아. 문법 오류 수정 후에도 재시도 통과 건의 숫자와 상세 목록이 어긋날 수 있어.
- 같은 스크립트는 최상위 `errors`를 집계하지 않아. workflow의 최종 판정도 요약의 failed 값에 의존해. 테스트 프로세스 종료 상태와 실행 오류를 함께 반영해야 해.
- 수정: 누락 변수, 중복 생성 경로와 키는 실행 전에 실패시키자. 보고서는 passed, failed, flaky, skipped, 실행 오류를 분리하고 재시도별 원인을 보존하자.

**새로 필요한 위험 검증**은 별도 후속 범위야. 기존 23개를 검증했다고 해서 다음까지 확보한 것으로 보지 말자.

| 옵션 필수, 품절, 최대 구매 수량 | 테스트 환경 UI와 API | 고정 상품, 재고 및 옵션 정책 |
| 두 상품 중 하나만 삭제, 동일 상품 재추가 | 장바구니 회귀 | 독립 데이터, 재추가 시 병합 정책 |
| 할인, 배송비 경계값, 도서산간 | 계산 단위 테스트와 API, 대표 UI | 확정 정책과 고정 가격 |
| 장바구니 이후 가격 또는 재고 변경 | 테스트 환경 통합 테스트 | 가격과 재고를 제어할 수 있는 준비 API |
| 결제 성공, 실패, 취소, 중복 제출과 콜백 | PG sandbox와 주문 API | sandbox 계정, 주문 조회, 정리 방법 |
| 인증 및 연령 제한 상태별 접근 | 테스트 환경 인증 fixture | 미인증과 인증 계정, 명확한 정책 |

## 4. 추천 구조

현재 저장소는 테스트 코드 저장소야. 서비스 백엔드 코드, 테스트 데이터 준비 API, staging 주소는 확인되지 않았어. 이를 이미 쓸 수 있다는 전제로 설계하지 말자.

```text
testcase-management/
  test-cases.csv          ID, 위험, 전제조건, 기대 결과, 우선순위, 상태
automation/
  tests/
    smoke/               핵심 사용자 여정
    regression/          정렬, 수량, 삭제, 주문서의 독립 검증
  pages/                 HomePage, SearchPage, ProductPage, CartPage, CheckoutPage
  fixtures/              guestSession, productData, cartWithProduct
  assertions/            상품 일치, 금액 계산, 목록 정렬 검증
  legacy/                이관 중인 기존 YAML runner
scripts/
  validate-testcases     명세와 spec 연결, 중복 ID와 상태 검증
  summarize-results      재시도와 실행 오류를 포함한 결과 집계
```

- **CSV는 검증할 내용을 관리해.** `risk`, `expected_result`, `data_profile`, `environment`, `automation_ref`, `owner`, `issue`, `review_due`를 필요한 순서대로 추가하자. 클릭 단계는 spec과 Page Object가 소유해. 같은 실행 로직을 CSV와 코드 양쪽에서 따로 편집하지 말자.
- **기존 YAML은 이관 기간에 유지해.** 새 spec으로 옮긴 TC만 기존 runner에서 제외하고, 이관된 ID가 새 spec과 연결되는지 검사하자. 모든 TC가 추적될 때 steps.csv 생성 체계를 폐기할 수 있어.
- **각 테스트의 상태는 독립적으로 준비해.** 현재 Playwright의 `page` fixture 격리는 재사용할 수 있어. 앞선 테스트가 장바구니를 채웠다는 전제를 만들지 말자.
- **전제 준비와 본 검증을 구분해.** 장바구니 편집 테스트는 준비 fixture를 쓰고, 장바구니 담기 테스트는 담기 동작과 완료를 직접 검증하자. 준비 API가 없다면 UI 준비부터 사용해.
- **Page Object는 UI 동작과 요소 범위를 담당해.** 가격, 수량 등의 기대 결과는 spec에서 읽을 수 있게 남겨. custom action에 모든 판단을 숨기는 방식은 피하자.
- **실제 상태를 기다려.** 담기 완료 안내, 장바구니 상품 행, 수량 반영을 기다리고 필요한 API 응답을 보조 증거로 쓰자. 고정 sleep이나 무조건 timeout 확대를 해결책으로 삼지 말자.

이 방향은 사용자에게 보이는 동작 검증, 독립된 테스트, 영역을 좁힌 locator를 권장하는 [Playwright 공식 원칙](https://playwright.dev/docs/best-practices)과 테스트별 준비와 정리를 지원하는 [fixture 문서](https://playwright.dev/docs/test-fixtures)에 근거했어. CSV 실행 DSL에서 직접 spec으로 옮기자는 선택은 이 저장소의 규모와 검증 요구를 바탕으로 한 추천이야.

Python으로 전체 재작성할 이득은 현재 근거에서 찾기 어려워. 이미 동작하는 TypeScript 기반 로딩과 Playwright 설정을 활용하는 편이 이관 범위를 줄여.

## 5. 운영 서버와 테스트 환경의 역할

| 구분 | 운영 smoke | 테스트 환경 회귀 |
|---|---|---|
| 목적 | 핵심 탐색과 승인된 구매 직전 경로의 사용 가능성 | 경계값, 실패 복구, 결제와 주문 정합성 |
| 데이터 | 승인된 격리 게스트 세션, 지정 상품의 사전 상태 확인 | 고정 상품, 계정, 재고, 가격, 테스트 주문 |
| 주문 및 PG | 최종 주문 또는 결제 동작 전 종료 | sandbox에서 성공, 실패, 취소, 중복과 지연 검증 |
| 외부 서비스 | 연결 지점의 UI 확인 | 통제된 응답과 sandbox를 목적에 맞게 분리 |
| 브라우저 | 먼저 Chromium 데스크톱 | 안정화 후 모바일 viewport, 실제 WebKit 등 우선순위별 확대 |

최종 결제 버튼을 누르지 않는 현재 범위는 **주문서 진입과 구매 준비 자동화**야. 결제 완료까지 검증하는 E2E라고 부를 근거는 없어. 주문서 버튼 노출만으로 주문서 작성 완료나 결제 가능 상태를 판단하지 말자.

운영의 상품 가격은 숫자를 코드에 고정하기보다 같은 여정에서 상품금액과 수량이 각 화면에 일관되게 전달되는지 확인하자. 할인과 배송비의 정확한 정책 검증은 고정 데이터가 있는 환경에서 독립적으로 해. UI 금액을 서로 비교하는 검사만으로 서버 계산 정책까지 올바르다고 입증할 수는 없어.

## 6. 구현 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 실행 신뢰성 복구 | 요약 스크립트 문법 정상, 누락 변수와 중복 키 차단, quarantine 분리, 실제 테스트 실패와 실행 오류 모두 CI 실패에 반영 |
| 2 | 대표 비회원 여정 1개 이관 | 새 게스트 상태에서 상품 확인, 담기 완료, 장바구니 식별값과 수량, 주문서 금액까지 증거 확보 |
| 3 | 23개 TC의 검증 목적 이관 | 위 매핑의 기존 ID 23개 모두 연결, 수량과 선택 상태 등 결과 assertion 추가, 분기별 실패 위치 구분 |
| 4 | 운영 지표와 회귀 확장 | 실행된 핵심 ID 누락 검사, flaky와 skip 별도 집계, 고정 데이터와 PG sandbox 확보 후 경계값 확대 |

단계 2의 다음 확인 대상은 장바구니 변경 허용 범위와 실행 가능한 브라우저 환경이야. 현재 자료만으로 담기 실패의 원인을 확정해 코드를 고치면 안 돼.

추천 안정화 기준은 핵심 묶음이 **서로 다른 새 세션에서 10회 연속 재시도 없이 통과**하는 거야. 이는 제안 기준이고 달성한 수치가 아니야. 운영 반복 실행은 승인된 실행 범위와 빈도 안에서만 해. 장기 운영 품질은 이후 일별 실패, flaky, skip 추세로 따로 평가하자.

리포트에는 통과율 하나 대신 다음을 남기자.

- 실행 대상 수, 실제 실행 수, 통과, 실패, flaky, skipped, 실행 오류
- 핵심 TC ID의 실행 누락과 quarantine 재검토 기한 초과
- 데이터 준비 시간과 본 검증 시간, 실패한 `test.step`
- 관련 TC ID, 상품 데이터 프로필, 환경, 재시도별 trace와 스크린샷

## 7. 이번 검토의 재현 명령

```bash
npm run testcases:check
npx tsc --noEmit
npx playwright test --list --reporter=list
node --check scripts/sync-testcases.mjs
node --check scripts/summarize-results.mjs
```

앞의 네 검사는 통과했고 마지막 검사는 실패했어. 실제 smoke 시도는 아래처럼 기존 실패 산출물을 덮어쓰지 않는 별도 경로로 실행했어.

```bash
TEST_TAGS=smoke npx playwright test --workers=1 --retries=0 \
  --reporter=json --output=/tmp/loma-review-20260907-results \
  > /tmp/loma-review-20260907-smoke.json
```

이 명령은 환경 권한 오류로 끝났고 사이트 동작은 검증하지 못했어. 로컬 로더를 직접 호출해 셀렉터 덮어쓰기, 누락 변수의 빈 문자열 치환, known issue 대상 2개, 장바구니 담기 준비를 포함한 11개 TC를 추가 확인했어.

기존 `test-results/`, `playwright-report/`, `test-health.md`는 과거 증거로만 참고했어. 현재 상태를 나타내는 새 성공 결과로 해석하지 않았어.
